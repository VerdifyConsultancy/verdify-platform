# Verdify vision CronJob

`verdify-vision` captures the two greenhouse camera frames from in-cluster
Frigate, analyzes them with the configured vision model, and persists the
result to Verdify's observation tables four times per day.

## Image + pull credential (ADR-0021)

The CronJob is part of the production overlay and inherits that overlay's
immutable `verdify-ingestor` digest: the manifest carries the canonical
`ghcr.io/...` image-name KEY only, and the `overlays/prod` images transformer
rewrites it to the pinned
`registry.vallery.net/verdifyconsultancy/verdify-ingestor@sha256:...` zot
digest. The pod pulls with the scoped `zot-origin-cluster-pull` secret only —
GHCR is retired (ADR-0021), and the transitional `ghcr-jvallery-readonly`
pull-secret entry was removed with #436 (its private-GHCR 401 was the original
failure mode).

## Mounted sources (GitOps-owned)

`ConfigMap/verdify-vision-src` is generated by this kustomization from `src/`
(it was hand-created out-of-band during the #436 recovery). The `src/` files
are byte-identical copies of the canonical sources — kustomize's RootOnly load
restrictor forbids reaching outside this directory, same pattern as
`components/firmware-twin` and `components/ha-gap-backfill`:

| `src/` copy | canonical source |
| --- | --- |
| `frigate-snapshot.py` | `scripts/frigate-snapshot.py` |
| `analyze-greenhouse-snapshot.py` | `scripts/analyze-greenhouse-snapshot.py` |
| `ai.yaml` | `config/ai.yaml` |
| `zones.yaml` | `config/zones.yaml` |
| `vision-analysis.j2` | `templates/vision-analysis.j2` |

`tests/test_20_vision_src_sync.py` (in the `make ci` gate) fails on any drift.
Edit the canonical file, then re-copy into `src/`.

## Operations

The schedule is live (`suspend: false` since the 2026-07-11 recovery canary:
53 s run, both cameras captured, two fresh `image_observations` rows).

Known wedge (`concurrencyPolicy: Forbid`): a Job that goes active with no pod
(observed live: `verdify-vision-29730060`, active since 2026-07-11T21:00Z with
zero pods) blocks every subsequent scheduled run. At the gated sync window the
operator deletes the wedged Job; the next scheduled tick reschedules normally:

```bash
kubectl -n verdify-prod get jobs -l app.kubernetes.io/component=vision
kubectl -n verdify-prod delete job <wedged-job-name>
```

For a one-shot canary after a sync:

```bash
kubectl -n verdify-prod create job --from=cronjob/verdify-vision \
  "verdify-vision-recovery-$(date -u +%H%M%S)"
kubectl -n verdify-prod wait --for=condition=complete \
  job/verdify-vision-recovery-<timestamp> --timeout=10m
kubectl -n verdify-prod logs job/verdify-vision-recovery-<timestamp>
```

Then verify `max(image_observations.ts)` advanced and the
`system.vision_pipeline` freshness alert clears.

## Connection refusals and recovery acceptance

The HTTPS service port 8971 deliberately targets the authenticated proxy's 8973
listener. Keep `cameras.vallery.net` TLS verification and the two allowlisted
`/api/vision/` routes; do not bypass authentication through port 5000.

When both cameras report `ConnectionRefusedError` before analysis, compare the
failed Job timestamp with the Sentinel-owned provider's availability and current
Service/EndpointSlice. A planned provider stop can fail one run while later
scheduled runs recover without a Verdify release. Preserve the original Job UID,
conditions and sanitized logs; check existing natural successes before submitting
a manual recovery. A healthy provider now does not explain its historical outage
without the owning rollout/incident evidence.

Use the controller's `batch.kubernetes.io/cronjob-scheduled-timestamp` annotation
and actual Job owner UID to distinguish natural runs from manual canaries. The
manifest declares no `timeZone`; do not infer UTC execution from its expression.

Acceptance requires both real camera captures, a terminal successful container
and fresh structured `image_observations` for both cameras with their linked
`observations`, not only an advanced maximum timestamp. Independently recheck
aggregate Argo health and retain old failures. A recovered provider and successful
scheduled Job require no whole-application sync. Any explicit prohibition on a
whole-application sync continues to apply.

[October 18/19 recurrence and natural recovery](../../../planning/reviews/2026-10-18-vision-recovery/README.md)
records the owning provider repair, two genuine analyses, six linked observations
and the unchanged source/image contract.

## Cortex route (#1021)

The image-input probe on Cortex #375 accepted fresh synthetic one/ten-image requests through `https://cortex.vallery.net/v1` / `llm.primary.longctx.mm`. Vision now uses the OpenAI-compatible client, one image/request, no automatic retries or cloud fallback, 90-second timeout and configured 4,096-token cap with thinking disabled. Truncated, empty or malformed JSON fails the run instead of inserting an accepted observation. The historical `observations.source=gemini-vision` remains the migration-268 SQL duty identifier and daily-plan selector; `image_observations.model` records the actual local route. This avoids silently broadening the runtime DB role. The old Gemini Secret is neither mounted nor deleted/revoked.

Production activation requires a dedicated scoped Cortex identity delivered through agents KSOPS; never project the operator or Frigate key into Verdify. Verify current egress to the gateway, exact GitOps revision/digest, and one real camera capture/analysis run with fresh database outputs before closing #1021. The bounded synthetic probe does not satisfy actual workload acceptance.
