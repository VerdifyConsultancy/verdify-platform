# Native API iterator nonprogress correction

Selected ESPHome2026.6.5 process_iterator_batch_ stops when the deferred batch grows or the iterator completes. Service-list responses and completion are sent directly. A false direct-send result leaves state/index and deferred batch unchanged; the enclosing loop retries indefinitely instead of returning to the normal application loop. This source path matches the newest collector crash's ListEntitiesServicesResponse/on_service stack. The prior254 crash and retained6ba protector observation do not independently identify a mutex owner or demonstrate reentry.

The correction adds a read-only state/index token to ComponentIterator and breaks the batching loop when advance makes no progress. It preserves the unsuccessful index, queued bytes and normal retry on the next application loop. Successful registration retains its full batch and unlimited legitimate service count; no new packet/entity cap, queue drop, scheduling yield, timeout, watchdog feed or control change is introduced. Both iterator and API generated files are full-hash guarded before any file is written; no SDK/global source is patched.

Native qualification compiles the actual selected ComponentIterator header/advance/process_item and ListEntitiesIterator::on_service with dependency types and a truthful writable/backpressure sink. The original method fails to return under persistent false sends; the corrected method returns after one failed item, resumes the same service in FIFO order, handles completion backpressure and preserves all620successful responses in one call. This is a real logical nonprogress reproduction, not an artificial sleep.

This fixes the proved nonprogress loop. It does not bound a single internal lwIP mutex operation; sys_mutex_lock still uses portMAX_DELAY. MSG_DONTWAIT/SO_SNDTIMEO do not change that mutex wait. Packet caps/yields cannot interrupt a stuck call; returning from a failed lightweight-protector lock without ownership would break mutual exclusion. Changing transport/core-locking or recursive mutex semantics is broader and lacks owner/nesting evidence here. Source/replay/native qualification is separate from actual firmware stability and live acceptance.
