# Prepared bounded production readback for Retry

Execution status: **not executed by the contained worker**. Retry owns all production operations. The request was sent to the root coordinator before any production query. Reuse an equivalent existing authoritative receipt instead of repeating it.

Run [production-role-metadata.sql](production-role-metadata.sql) once through the supported existing production peer/owner connection after recording the exact DB Pod UID/container/image, owning source revision and read-only executor scope. Bind the same identities after completion. The transaction is repeatable-read READ ONLY, has10s statement/1s lock timeout, ends ROLLBACK and exports only fixed role/catalog/ledger metadata and existing client-role/IP counts. It does not read passwords/verifiers, Secret data, query text, application rows or change session authorization. A missing relation/role is a retained mismatch, not permission to repair it.

For the nine selected workloads in [desired-workload-authority.json](desired-workload-authority.json), capture only:

* Current controller UID/generation and actual owned Pod UID/IP/node/imageID/restart/Ready metadata; the CronJob template and latest owned Job status if a scheduled duty is presently idle.
* Env **names and reference kind/name/key only**, envFrom reference names, Secret volume names and service-account binding. Allowlist public role literals and required-role booleans; redact literal DSNs, passwords, tokens and all other env values. Never GET/LIST Secrets, inspect last-applied annotation values or dump process environments. Include init containers as well as ordinary containers.
* Whether real source startup role-attestation has passed for API/ingestor/MCP/planner and the other source-guarded callers at their current image; bounded current permission/identity-error counts and successful normal duty status from retained logs. Avoid full logs/product payloads. API/ingestor credentials whose username is a Secret key are proved through the real attester/current backend, not by reading that key.
* Exact two adjacent CronJob owner-password reference structures (`verdify-writer-watchdog`, `verdify-band-curve-refresh`) and existing successful duty status/error summary. Backup, migration, bootstrap and DB server authority are separately classified; no blanket owner-credential rotation follows.
* Existing effective RBAC for only the selected `default` and `verdify-ingestor` ServiceAccounts: Secret get/list, Pod exec, and workload/Job creation or replacement authority that could acquire a different credential. Reuse the owner's current binding receipt if available. Product source grants the ingestor its writer lease only, but does not disable the default token mount; that source fact cannot rule out an inherited estate binding. Export permission booleans or relevant binding/rule metadata only, never tokens or Secret data.

Join existing session `client_addr` to captured PodIPs. Zero sessions on a short-lived workload proves no execution; report it as absent. Source required flags plus Ready alone are not an authenticated backend result. A current backend catalogue join is an observation, not an active role allow/deny fault test. Do not start a job, force a plan, call a mutation endpoint or authenticate with a copied credential solely to fill the sheet.

The source worker can finish the sanitized rollout/inverse worksheet while this readback is pending. No new Jason decision is required for these authorized metadata reads. Any later production credential action is asked only after exact missing identities, owner mechanism, rollout and inverse are concrete.
