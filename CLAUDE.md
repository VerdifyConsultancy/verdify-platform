# verdify-platform

Source of truth for the live Verdify greenhouse product: the ESP32 controller firmware, the ingestor (the only device writer), the TimescaleDB schema and migrations, the API, MCP, the Iris planner, the experiment-v2 orchestrator, the lab.verdify.ai Quartz site and product Grafana, plus the k3s desired state for namespace `verdify-prod`. Lane: **Verdify greenhouse product** — the estate lane map and placement rules live in `jvallery/agents` at `docs/estate/README.md`.

## Operating contract

Jason's direct request authorizes the work it describes, across code, infrastructure, and Jason-owned services in scope, through delivery and verification of the real end state. Ask only when an unresolved ambiguity could materially change the outcome. Add approval, review, issue/PR, or planning steps only when Jason asks for them or a branch rule enforces them; process descriptions in repository docs are context, not gates.

- Make the smallest complete change in the repository that owns the thing being changed (see Ownership). Fix forward; prefer rollback when it restores service faster or limits harm. Skip speculative abstractions and unrelated cleanup.

Reuse existing CI/CD, honor enforced checks, and add pipelines or gates only for a concrete need in the task.

- Search narrowly, batch independent lookups, reuse current evidence, and keep plans and updates brief.
- Use existing credentials without printing, committing, or logging secret values or Kubernetes Secret data; rotate or revoke credentials only when Jason asks.

## Deliver and verify

- Images: a merge to `main` triggers the in-cluster `repo-build` (Kaniko) for the images in `.agent-fleet/ci.yaml`. The `verdify-platform-ci` pin actuator then commits digests for api, mcp, ingestor, migrate and experiment-v2-orchestrator to `deploy/k8s/overlays/prod/kustomization.yaml`, so hand edits to those lines race with it. The planner, setpoint-server and lab-publisher digests are pinned by hand: the merge's `verdify-platform-ci` run builds them too, so take the `digest` output of that image's build step, or resolve its `sha-<first 12 characters of the commit>` tag on the zot origin, and commit a digest-only change. An image outside `.agent-fleet/ci.yaml` (today `verdify-twin`) still needs the manual `repo-build` submission in `docs/runbooks/prod-promotion.md` Flow step 3.
- CI: `make ci` (`scripts/ci-local.sh`) is the full offline gate. In-cluster CI posts the commit status `Verdify Platform / Argo PR CI` on PR head commits; read it with `gh api repos/VerdifyConsultancy/verdify-platform/commits/<sha>/status`. This repo produces no check-runs, and `gh run list` shows only retired Actions history. `.github/workflows/` is expected to stay empty (`tests/test_no_hosted_runner_workflows.py`).
- Production: Argo app `verdify-prod-dark` (destination `verdify-prod`, path `deploy/k8s/overlays/prod`, `targetRevision: main`) has manual sync and prune off, so a merge changes Git only. The explicit sync is the device-write gate, and it Recreates the single ingestor when its pod spec changes. Sync only when the request covers it. Mechanics: `docs/runbooks/laptop-operator.md` §2 and `docs/runbooks/attended-convergence.md`.
  - Diff first: `kustomize build deploy/k8s/overlays/prod | kubectl diff -f -`. A sync applies every OutOfSync resource, not only yours, so check any pending drift against the request.
  - Normal path: a plain full sync with `prune: false` and no `resources`. It runs the ledgered `verdify-migrate` and bootstrap PreSync hooks and the gate-r readiness PostSync Job.
  - Read `.status.operationState.operation.sync.resources` right after submitting; it must be absent or empty. If resources appear (the [#317](https://github.com/VerdifyConsultancy/verdify-platform/issues/317) rewrite) or the result covers too few resources, stop and do not retry.
  - The explicit `resources:` vector (`scripts/gen-sync-resource-vector.sh`) is a reviewed fallback only. Argo CD skips every hook on a selective sync, migrations included, and does not record it in history, so new api, ingestor or mcp digests would run against an unmigrated schema. Use it only for a change with no migration or hook part; every pin commit from the actuator bumps the `verdify-migrate` digest.
  - Never prune the `verdify-db` StatefulSet/PVC or the `verdify-db-dumps` PVC.
- Verify production: `kubectl -n argocd get application verdify-prod-dark -o jsonpath='{.status.sync.status} {.status.health.status} {.status.sync.revision}'`; `kubectl -n verdify-prod get deploy,sts,cronjob`; `scripts/k3s-smoke.sh smoke` (API, MCP and DB health) and `scripts/k3s-smoke.sh device-monitor` (exactly one ESP32 connection). After an ingestor rollout, watch `kubectl -n verdify-prod logs deploy/verdify-ingestor` for `ValidationError` or `row failed schema validation` for five minutes.
- Firmware reaches the controller through `make firmware-deploy` or its manual equivalent in `docs/runbooks/k3s-operations.md` §4, both behind `scripts/firmware-deploy-preflight.sh`. The make target runs the preflight, refuses a dirty tree, compiles, flashes over OTA, runs a sensor-health sweep, and rolls back to `last-good` on failure. The preflight blocks on an unresolved critical alert, stale telemetry, a missing or under-48-hour-old last-good artifact, or a firmware version already first seen this calendar week; its override variables require a written reason, so use them only when the request covers overriding that gate.
  - The Makefile passes `VERDIFY_DB_BACKEND=kube` only to the preflight. The post-OTA version wait and sensor-health sweep otherwise use the docker backend of the decommissioned VM, time out, and flash last-good back over a healthy OTA. Export `VERDIFY_DB_BACKEND=kube` for the whole run, or follow the manual sequence in `docs/runbooks/k3s-operations.md` §4 (which also covers the pinch reset each flash causes).
  - Verify with the `diagnostics.firmware_version` query in `docs/runbooks/laptop-operator.md` §3, not `firmware/artifacts/last-good.version`, which is the rollback floor and lags during the bake.
- Lab content: S3 content → `verdify-lab-publisher` CronJob (every 10 minutes) → validated PVC generation → content-free nginx; checks in `docs/agents/web.md`, operations and rollback in `docs/runbooks/lab-content-pipeline.md`.

## Working here

- Authoritative docs: `ARGOCD.md` (Application and sync model); `docs/runbooks/k3s-operations.md` (operating model, dev loop, OTA, and §6 durable gotchas); `docs/runbooks/laptop-operator.md` (DB, sync and OTA commands, runnable from any kubectl host); `deploy/k8s/SECRETS.md` (Secret names and keys); `docs/CONTROL-ARCHITECTURE.md` and `docs/firmware-control-contract.md` (control authority); `docs/firmware-fsm-spec.md` (state machine and invariants); `docs/agents/web.md` (lab pipeline). `docs/RUNBOOK.md`, `docs/SYSTEM-ARCHITECTURE.md` and `docs/verdify-migration.md` describe the decommissioned VM deployment ([jvallery/agents#4491](https://github.com/jvallery/agents/issues/4491)).
- Generated files; edit the source instead: `PROJECT_BOARD.md`, `LANES.md`, `MILESTONES.md`, `SPRINTS.md`, `EPICS.md`, `planning/DEPENDENCIES.md` and `planning/issues_manifest.json` come from `planning/backlog.yaml` (`python -m planning.render`; `make planning-validate` checks them and `make ci` does not); the dashboard ConfigMaps in `deploy/k8s/components/grafana/generated/` come from `grafana/dashboards/` (`python scripts/gen-grafana-dashboard-cms.py`, checked by `make grafana-cm-check`).
- Cross-layer contracts:
  - Land a `verdify_schemas` model and its migration before or with their consumers; `verdify_schemas/tests/test_drift_guards.py` guards the layer boundaries. Every ingestor DB write validates through a `verdify_schemas` model, and a new external API input gets a boundary schema in `verdify_schemas/external.py`. Before tightening a `verdify_schemas` write model, check live data or inputs for rows that would now fail, because the single ingestor logs and drops any row that fails validation.
  - Migrations are serialized, one numbered file per change. Never edit an applied migration; the ledger runner fails closed on a changed hash. Never wrap a self-committing migration (a top-level `COMMIT`, or `CONCURRENTLY`, `VACUUM`, `ALTER SYSTEM` and similar) in an outer `BEGIN … ROLLBACK`: the inner commit lands on the live database, as it did on 2026-05-30. `make migration-rollback-safety` classifies each file.
  - `ALL_TUNABLES` in `verdify_schemas/tunables.py` is the planner/firmware tunable contract; the firmware exposes a tunable before the planner uses it. Each new `num_*`/`sw_*` tunable in `firmware/greenhouse/tunables.yaml` needs a `cfg_*` readback in `firmware/greenhouse/sensors.yaml` ("rule 6" in code comments), because a fire-and-forget tunable can be corrupted silently on push.
  - A change to `verdify_schemas/**`, `ingestor/entity_map.py` or `mcp/server.py` names its restart in the commit message or PR body, as `Post-merge restart: verdify-mcp, verdify-ingestor` or `Restart: none — <reason>` ("rule 7", `scripts/check-service-restart-drift.sh`), because MCP once served a stale schema for 40+ hours.
  - New override flags go in `firmware/lib/greenhouse_types.h` and every consumer; a `firmware/greenhouse/controls.yaml` entity rename or removal updates `ingestor/entity_map.py`.
- Hazards:
  - Device writes happen only when `VERDIFY_DEVICE_WRITE_ENABLED=1`: the code gate defaults to deny (`tests/test_device_write_gate.py`), and only `overlays/prod` sets it to 1. Keep the ingestor at replicas 1 with `strategy: Recreate` so two writers never reach the ESP32. `verdify-setpoint-server` is a second device-affecting writer (Home Assistant grow lights), prod-only and hand-pinned; `tests/test_setpoint_server_db_backend.py` keeps its pin from regressing to the pre-#447 digest.
  - Targets that touch production: `make test` and `make check` (run `tests/` against the live stack), `greenhouse-quiet-on`/`-off` (setpoints), `irrigation-feedback-finalize`, `irrigation-acceptance` and `irrigation-feedback-clear-stale-*` (resolve DB alerts, clear retained MQTT topics), `hermes-restart` (restarts the prod Hermes Deployment), `db-dump` (overwrites `db/schema.sql`), and `firmware-deploy`/`firmware-rollback` (flash the controller). `scripts/verdify-db.sh prod` reaches the DB through `kubectl exec` into `verdify-db-0`. `scripts/smoke-feedback-loop.py` is built for the live stack: it inserts synthetic `setpoint_changes` rows (one deliberately mismatched) into the DB it reaches, runs the setpoint confirmation monitor so it writes a `setpoint_unconfirmed` row to `alert_log`, and deletes both afterwards. `ingestor-restart`, `ingestor-logs`, `hermes-deploy-config` and `hermes-smoke` target the decommissioned VM and do nothing useful on k3s.
  - `kustomize build deploy/k8s/overlays/prod` must emit zero `kind: Secret`: each `*.placeholder.yaml` Secret carries `config.kubernetes.io/local-config: "true"` as an annotation, because as a label it renders and the AppProject rejects the whole sync. `make firmware-deploy` reads the OTA password from the cluster; never print it.
  - The descheduler is applied with kubectl, not Argo. Live runs in enforce mode while `deploy/k8s/descheduler/cronjob.yaml` still has `--dry-run`, so `kubectl apply -k deploy/k8s/descheduler` silently disarms it. [#802](https://github.com/VerdifyConsultancy/verdify-platform/issues/802) brings Git to live and puts it under Argo.
  - `verdify-tier1-forward` sends every single-label `*.verdify.ai` host its match does not exclude to this repo's tier-2 Traefik. Any such host routed outside `verdify-prod` must be in that exclusion list, because Traefik priority is not an ownership mechanism ([#801](https://github.com/VerdifyConsultancy/verdify-platform/issues/801) adds www-dev and proposals-hello).
- Focused commands:
  - `make setup` (repo `.venv`); `make ci`; `CI_BASE_REF=origin/main make ci` adds the diff gates (rules 6 and 7, and the firmware replay diff at `THRESHOLD_PCT=0`); `make lint`/`make format`; `kustomize build deploy/k8s/overlays/prod`.
  - Firmware logic (`firmware/lib/**`, `firmware/greenhouse/**`, including any structural `greenhouse_logic.h` change): `make test-firmware`, `make firmware-invariants`, the replay diff (`make firmware-replay-worktree OLD=<ref>` before committing, `make firmware-replay OLD=<base> NEW=HEAD` after), plus `make firmware-replay-band OLD=<base>` for band-curve changes, which the corpus-fed replay reports as zero divergence; then `make firmware-check`.
  - Planner prompts or model: `make planner-dry` (renders every event type, no API call) before shipping; compare plan-cycle cost and investigate a rise above 20%.
  - Lab and site: `make site-doctor` plus the checks in `docs/agents/web.md`.
